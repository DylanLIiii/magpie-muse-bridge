# Real Muse account check on large-vps

Environment: Muse Code 1.4.14 (1.4.14-R7309.1), Magpie 0.1.2888, Node 22.23.4.
The installed plugin and the server checkout both use main commit `5a954ae`.

Observed results:

- The existing Muse login passes `muse usage --json`, but returns
  `allowance: null`, `reason: server_sent_no_usage`.
- Meta's `/muse-code/models` and `/v1/models` return HTTP 200 with `data: []`
  using the stored Muse API credential. No credentials were printed.
- Official `muse exec` with no explicit model fails with
  `failed to fetch model catalog: model catalog has no visible models`.
- Official CLI requests for Spark 1.3, Wonder 1.0, and Wonder Full 1.0 all
  fail with `model ... does not exist or you lack access`.
- The installed plugin returns 502 for the same upstream failure. The live
  Magpie gateway returns HTTP 200 SSE containing an error, without an answer.
  Existing gateway logs show repeated failures taking roughly 49–52 seconds.
- The native CLI bootstrap log records `credential.refresh`,
  `outcome="success"` at 2026-11-04 06:03:23 UTC.
- In a private temporary copy of the credential, removing only the cached
  `api_key` and running the official CLI's usage command reacquires the same
  API key. That key still returns an empty catalog; a direct Wonder request
  fails with request ID `3a774eb5-9fd5-486a-a710-3fe685182b80`.
  The source credential file remained unchanged by this isolated experiment;
  the temporary credential copies were removed afterward.

After the user completed a fresh browser sign-in:

- The native bootstrap log records `credential.login`, `surface="login"`,
  `outcome="success"`, as well as a successful credential refresh.
- The CLI and plugin both read `/root/.config/muse/auth.json`. No alternate
  `XDG_CONFIG_HOME`, `MUSE_AUTH_PATH`, or `META_API_KEY` masks this login in the
  test shell.
- The model catalog still returns HTTP 200 with `data: []`.
- Official CLI Wonder requests fail with Contributor mode off (request ID
  `a6e0d134-f765-4171-b871-442a5e374413`) and on (request ID
  `46985f53-926f-491f-a9a9-9f268005a781`). The patched SDK bridge also fails
  (request ID `cec90d03-2628-4d32-b74a-574d26b939a6`).
- The egress-country lookup reports US; the test shell has no configured proxy.
  Meta's unauthenticated `/v1/status` returns `is_alive: true` and
  `service_status: operational` with an empty per-model status list. These
  checks do not establish account-specific or per-model service health.
- The user confirmed model entitlements on the subscription page, but has not
  yet obtained a successful native Muse response on another machine.

These results establish that the server's current login cannot run a model in
the official CLI either. They do not establish that the user's account lacks a
subscription or model entitlement. Refreshing and reauthenticating did not
resolve the failure. A subscription-to-CLI entitlement issue, an account mismatch,
or a server/network-specific issue remain possible; these observations do not
distinguish them.

The patched plugin was tested in `/root/.cache/muse-bridge-live-20261104`,
separately from the installed plugin. Its real-account smoke test exits 1 at
the first model request and reports HTTP 404 `not_found_error`, preserving the
request ID and sign-in instead of suggesting a transient 502 retry. No real
model answer or MCP round trip has succeeded, so those remain unverified.

The local deterministic suites pass under Node and Bun. On large-vps, Muse
1.4.14 against a local fake upstream passes the SDK and legacy exec regression
checks, including tool round trips and the new model-access error mapping.

Next discriminating check: run the official Muse CLI on another machine with
the same account. Success there would narrow the problem to the VPS environment
or its CLI credential; the same failure there would favor an account/CLI
entitlement issue. The request IDs above can be supplied to Meta support for
account-specific investigation. The live gateway's installed plugin has not
been replaced; the patch improves failure reporting and does not restore model
access.
